# Complexity policy

Omakure's complexity evidence is generated by the pinned native `cccc` report.
The report is informational until the changed-function gate compares it with
`quality/complexity/baseline.json`; it does not implement a custom complexity
algorithm.

## What is measured

- **Cyclomatic complexity** counts the native analyzer's control-flow paths.
  A new or regressed handwritten function is a review trigger only when its
  score is greater than 10.
- **Cognitive complexity** is the native analyzer's nesting/readability score.
  A new or regressed handwritten function is a review trigger only when its
  score is greater than 15.
- **Size** (SLOC/PLOC/LLOC where the native report supplies it) and **nesting**
  accompany a trigger as evidence; neither silently changes the gate.
- **Coverage** is current supporting evidence from the coverage workflow, not a
  complexity score or a required branch-coverage threshold.

Clippy remains advisory. Clippy warnings are never described as a true
cyclomatic-complexity measurement.

## Ratchet and identity

`scripts/tasks/complexity-gate` compares the canonical native rows with the
reviewed baseline. A row's key is its normalized repository-relative path plus
its qualified source signature. A path or signature rename is intentionally a
delete plus an add, so the replacement receives the new-function policy.
Unchanged legacy hotspots remain informational and do not fail the gate.
Generated and dependency-classified sources are retained in evidence but are
not changed-function gates; unclassified source fails closed.

The gate writes deterministic per-function evidence and trend rows to the
requested output. Baseline, source accounting, native tool/config identity,
canonical hashes, parser status, and (when supplied) an independently repeated
report are all checked before a decision is made. Missing baseline data, tool
or config drift, parse/source classification failures, and nondeterministic
reports fail closed.

## Exceptions

`quality/complexity/exceptions.json` is a reviewed, versioned registry. Every
entry requires an accountable owner, UTC `created_at`, `reviewed_at`, and
`expires_at` timestamps, native analyzer/tool/config identity, exact path and
symbol, separate cyclomatic/cognitive ceilings, rationale, and passing focused
test IDs. Review and expiry must be ordered and no more than 90 days after
creation. Expired, stale, drifted, widened, malformed, or untested entries are
rejected; renewal is a replacement reviewed with new evidence, never an
automatic extension. An exception permits only its recorded ceiling and never
permits a score above that ceiling.

## Local and CI use

Acquire the pinned analyzers before generating a report:

```text
mise run quality:complexity-setup
mise run quality:complexity-report
mise run quality:complexity-gate
mise run quality:complexity-gate-test
```

The dedicated CI workflow runs two native reports, gates the first against the
second for deterministic output, publishes the gate's per-function evidence,
and maintains the temporal informational soak. The soak audit records trusted
successful runs and reports whether the chain has ten consecutive records
spanning at least seven calendar days. This evidence is informational and does
not weaken local changed-function enforcement.

The soak proves that the pinned analyzer keeps producing the same output for
the same input across days and runners. Each record therefore carries the
analyzer's identity (version, binary digest, configuration, output schema digest) and the
canonical hash of the fixed fixture corpus, and a streak continues only while
both stay constant. The canonical hash of the live source tree is recorded as
evidence of that run and is allowed to change between records, because merged
code changes it. A deliberate change to the analyzer, the corpus, or the state
format restarts the streak with the reason recorded in the persisted state,
the same way a missing trusted run does. The state retains at most ten
records; when the window lets its oldest record go, the digest of that record
is kept as `pruned_record_sha256`, so the first retained record still links to
a known predecessor and pruning never loosens the chain.
